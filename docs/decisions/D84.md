# D84 · The forks of a sequence run in its order

Domain. Host.
Decision. The evaluator runs the forks of a sequence one after another
in its order: the elements under `*`, of a vector, of a set, the entries
of a map and of an error literal, the modifiers of a command [D12], the keys
of `sort` and the examples `runExamples` runs; each result stands where
its element stood. An operand of a host with an effect therefore meets
the elements in their order, and a host whose operand is better served
by calls at once takes the whole vector and bounds its own calls. A
pure pipeline cannot observe the order, so the requirement is held by a
host's operand that records its calls.
Source. The model's proposal of 26 September, `*` made sequential, the
order one everywhere and predictable for a model, simultaneity useful
only for a host's input and output and bounded by the host that knows
its limit, accepted: «а так согласен с "Я бы сделал * последовательным"
.. твои доводы убедительны» (maintainer, 2026-09-26 06:10, session
86982eb5). The cost falls on the sister project, whose model liked the
fan-out: «@members * @callers .. там периодически такое происходило .. у
java.lang.String вызывали и получати под 200 мемберов и у каждого там
десятки тысяч точек вызова в зависимости от класспаса» (maintainer,
2026-09-26 06:10, session 86982eb5).
Set aside. The fan-out of `*` and of the vector literal with simultaneity
left unspecified, the rule this audit first wrote, under which an effect
inside `*` shows the order of completion and ten thousand elements issue
ten thousand simultaneous calls. A second combinator, `**`, that forces
one way or the other, and hands a query a simultaneity nothing bounds.
