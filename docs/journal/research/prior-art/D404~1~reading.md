# Разбор поиска чужого опыта для открытой записи D404 на ветке the-text-read-once

Чтение модели, сессия 4fde8c60, 2026-10-21. Отчёт — [D404~1.md](D404~1.md):
исследователь, которого сессия запустила, пока ветка работала вопрос
[D404], по словам мейнтейнера «может ресерчни в сети каким агентом, что
есть в peggy против экспоненциальных всяких взрывов.. может уже в сети
расписаны приемы и т.п.». Он читал рабочее дерево ветки на базисе
78cd2e3e, 14:26–15:14 UTC. Вывод отчёта: память неудач по месту и
признакам состояния, где неудача, прочитанная молча, служит только
молчаливым чтениям, — известный приём, а готового средства в peggy нет.
Его предупреждение о повторных удачных чтениях подтвердилось: на
правильном вводе нашлась экспонента, которую память неудач не ловит, и
ветка её убрала.

Промпт, на который он отвечал:

```text
Исследуй в сети (WebSearch и WebFetch; если они отложены, загрузи их через ToolSearch), что есть у генератора парсеров Peggy (peggyjs/peggy, наследник PEG.js; у нас версия 5.1.0) и в практике PEG-парсеров против экспоненциального роста времени разбора из-за отката (backtracking) — когда одно и то же место текста перечитывается разными альтернативами.

Контекст, чтобы искать прицельно. Мы пишем грамматику языка запросов на Peggy. Разбор незакрытого вложения (например, `f ~(f ~(f ~(` … без закрывающих скобок — так выглядит текст до курсора в языковом сервере) рос как 4^n: после неудачи чтения слова как модификатора команды то же слово перечитывалось как следующий модификатор, затем упреждающими проверками отказов (`&Word`) и т. д. У грамматики есть глобальное состояние, которое меняют семантические предикаты: счётчики глубины (`docQuoteDepth`, `lookingAhead`) и флаг (`spanOfALine`); результат правила на месте зависит от них. Мы сейчас сделали так: для нескольких «вкладывающихся» правил (группа в скобках, цитата `~(…)`, тегированный литерал, вложенные блочные комментарии и доки) держим в инициализаторе типизированный массив неудач по ключу (offset, биты состояния); перед чтением правила семантический предикат проверяет, не падало ли оно уже здесь, и при неудаче альтернатива с предикатом записывает неудачу. Неудачу, случившуюся внутри упреждающей проверки (`peg$silentFails > 0`, ожидания не записываются), используем только для чтений внутри проверок, а неудачу «вслух» — для любых, чтобы список ожидаемых продолжений в ошибке (`expected`) не терял элементов. Внутреннюю переменную `peg$silentFails` читаем из кода инициализатора. Чтобы Peggy не ругался «Possible infinite loop … repetition used with an expression that may not consume any input», альтернатива, записывающая неудачу, заканчивается потребляющим выражением, до которого дело не доходит (`&{ return failedHere(...); } "("`).

Что выяснить (с источниками — URL, по возможности документация Peggy, исходники, issues и обсуждения на GitHub peggyjs/peggy и pegjs/pegjs, статьи):
1. Опция `cache` (packrat) в Peggy 5.x: что именно она кэширует (успехи и неудачи? по паре правило+позиция?), цена по памяти и времени, как она взаимодействует с семантическими предикатами и глобальным состоянием, с упреждающими проверками и с собиранием `expected` для ошибок (не теряются ли ожидания при попадании в кэш). Есть ли кэширование для отдельных правил (выборочное), плагины, флаги правил, `--allowed-start-rules`, что-то в новых версиях (4.x, 5.x changelog).
2. Есть ли в Peggy официальный или полуофициальный доступ к `peg$silentFails` (например, `options.peg$silentFails`, режим `library`/`peg$library`), насколько это стабильно; есть ли другой способ узнать в предикате, что мы внутри упреждающей проверки.
3. Есть ли в Peggy оператор отсечения (cut, как в работах Мидзусимы и др. о PEG cut) или аналог; есть ли в обсуждениях Peggy предложения такого рода.
4. Известные приёмы против экспоненциального отката в PEG: левая факторизация, вынесение общего префикса, «читать один раз и решать по прочитанному», выборочная мемоизация только неудач, мемоизация с учётом состояния, ограничения packrat при семантических предикатах с побочными эффектами, «elastic» мемоизация, работы о селективной мемоизации (например, Rats!, Mouse, «Packrat parsing: simple, powerful, lazy, linear time» Форда, работы Редзиевского о Mouse, работы о cut), их применимость к Peggy.
5. Как другие проекты на Peggy/PEG.js решали проблему медленного разбора незакрытых конструкций в редакторе/языковом сервере (восстановление после ошибок, ограничение глубины и т. п.).
6. Есть ли в Peggy способ подавить предупреждение/ошибку про бесконечный цикл без фиктивного потребляющего выражения, и не ломает ли наш приём что-то.
```

1. **`cache` peggy неверен для этой грамматики.** Он кэширует успех и
   неудачу по паре «правило + место» без состояния разбора и без
   ожиданий: исследователь воспроизвёл на 5.1.0 потерю продолжений в
   отказе (pegjs#452) и обратный смысл разбора при счётчике, который
   меняют действия. Судьба: дорога отставлена в [D404] с этими
   источниками; сборка парсера кэша не включает.
   ```sh
   $ grep -c "cache" core/scripts/build-grammar.mjs
   0
   ```

2. **`peg$silentFails` — внутренность peggy, стабильная с 2013 года.**
   Её читает и автор peggy из инициализатора своего проекта; при
   переименовании разбор упадёт громко. Счётчик растёт и внутри правила
   с именем, `Whitespace "whitespace"`, и неудача там пишется как
   молчаливая: она служит только молчаливым чтениям, что осторожно и
   верно, потому что такое чтение не пишет продолжений. Судьба: [D404]
   держит это деление и называет, кто его читает.
   ```sh
   $ grep -c 'peg$silentFails' core/src/grammar.peggy
   2
   ```

3. **Отсечения в peggy нет, его выражают предикатами: прочитать один раз
   и ветвиться по прочитанному.** Судьба: ветка так переписала первый
   модификатор команды (касающийся имени `(` и следующие за пробелом) и
   объявление (имя и доки читаются один раз, форма тела выбирается
   предикатами в прежнем порядке проб); перечитывание слова отказами
   пробелов осталось на памяти неудач. В [D404].

4. **Приёмы из работ подтверждают устройство.** Выборочная память правил
