**Вердикт.** На однородных данных `shape` хорош: API-ответ с вложенными записями сворачивается в компактную схему, она читается как тип TypeScript, а путь данных (`/data/users/0/address/city`) читает её же. На данных, которые чаще всего встречаются посреди задачи, он подводит в трёх местах.

1. Одно необязательное поле разбивает элемент вектора на множество вариантов записей. Тогда путь `/users/0/age` по схеме уже не читается, а 6 необязательных полей дали 62 варианта (5187 символов). Чтобы узнать, есть ли поле всегда, приходится сравнивать варианты глазами.
2. `::each` сворачивает по совпадению формы, а не по тому, что ключи — данные. Поэтому имена `:db`/`:cache` пропадают. Мапа из 365 дат в числа не сворачивается вовсе, и её схема (9880 символов) больше самих данных (7951 байт). При этом путь данных `/by_id/17/name` по схеме падает с ошибкой.
3. Тег и множество скрывают своё содержимое (`::Box`, `::set`). Размеров нет нигде.

Ниже предлагаю форму с `::absent` в объединении вместо вариантов записей. Она строится из литералов, которые в qlang уже есть.

### 1. API-ответ с вложенными записями, массивами и null

Ожидал: одну запись в `:users`, `:email` как `#[::null ::string]`, `:roles [::string]`, `:next ::null`.

```
> {"data": {"users": [{"id": 1, "name": "Ann", "email": "a@x.org", "roles": ["admin"], "address": {"city": "Riga", "zip": "1001"}}, {"id": 2, "name": "Bo", "email": null, "roles": [], "address": {"city": "Oslo", "zip": "0150"}}], "page": 1, "total": 2, "next": null}} | shape
::shape{
  :data {
    :users [
      {
        :id ::number
        :name ::string
        :email #[::null ::string]

    :page ::number
    :total ::number

  }
}
> {"data": {"users": [{"id": 1, "address": {"city": "Riga"}}]}} | shape | get /data/users/0/address/city
::string

::number
```

Совпало с ожиданием. Сразу понятно, что писать: `get /data/users | map ~(query /email)`, `/roles` нужно считать, а не читать `/0`. По форме это `interface` из TypeScript без `?`. Не хватает одного: схема не говорит, что `roles` бывает пустым, а `total` равен 2. Вектор `[::string]` выглядит одинаково при 0 и при 10⁶ элементов.

### 3. Записи с разными наборами ключей

Ожидал: варианты вперемешку. Хотел узнать, какие поля есть всегда.

```
> [{"a": 1}, {"b": 2}, {"c": 3}, {"d": 4}, {"a": 1, "b": 2}] | shape
::shape[#[{:a ::number} {:a ::number :b ::number} {:b ::number} {:c ::number} {:d ::number}]]
> [{"id": 1, "x": 1}, {"id": 2, "x": null}, {"id": 3}] | shape
::shape[
  #[
    {:id ::number}
    {
      :id ::number
      :x #[::null ::number]
    }
  ]
]
> [{"u": {"a": 1}}, {"u": {"a": 1, "b": 2}}] | shape
::shape[
  {
    :u #[{:a ::number} {:a ::number :b ::number}]
  }
]
> [{"v": [1]}, {"v": {"x": 1}}, {"v": "s"}] | shape
::shape[
  {
    :v #[::string [::number] {:x ::number}]
  }
]
> [{"a": 1}, null, {"a": 2}] | shape
::shape[#[::null {:a ::number}]]
> [{"a": {}}, {"a": {"x": 1}}] | shape
::shape[
  {
    :a #[{} {:x ::number}]
  }
]
```

Правило «не вшивать ключ, которого у записи нет» соблюдается честно: схема не врёт о совместной встречаемости полей. Но варианты не помечены ни частотой, ни общим ядром. Пустая мапа `{}` отделяется от `{:x ::number}`, хотя пустой вектор уступает непустому. Это несимметрично: для того, кто читает `/a/x`, `{}` значит то же самое, что «`x` пропущено». Полиморфный `:v` показан хорошо, примерно как `string | number[] | {x:number}` в TypeScript.

### 5. Глубокая вложенность, вектор векторов

Ожидал: вложенные `[[…]]` и полный путь до `:g`.

```

::shape{
  :a {
    :b {
      :c {
        :d {
          :e {
            :f [{:g ::number}]
          }
        }
      }
    }
  }
}
> [[1, 2, 3], [4, 5], []] | shape
::shape[[::number]]
> [[1, "a"], [2, "b"]] | shape
```

Глубокая вложенность читается хорошо, но печать по одному ключу на уровень тратит строки. Для `/a/b/c/d/e/f/0/g` в такой цепи jq-шный `paths` короче.   :"2024-01-03" ::number

- **Ложное сворачивание.** `:db`/`:cache` и `:home`/`:work` — это имена полей. После `::each` я не знаю, что писать `get /config/db/host`: ключи стёрты, и за ними нужно идти отдельным `keys`.
- **Пропущенное сворачивание:**
  - Даты, ведущие к числам, не сворачиваются: «мапа атомов хранит ключи». На 365 датах это стоит больше самих данных (случай 8).

  - Одно `null` среди строк тоже ломает сворачивание.
- **Путь данных не читает схему.** `/by_id/17/name` падает, а работает `/by_id/name`. Страница это оговаривает («past the key a fold stands for»), но обещание «the paths of the data read its shape» здесь неверно буквально.

`::each` по смыслу совпадает с `Record<string, T>` / `additionalProperties` из JSON Schema, только без хотя бы одного примера ключа. По схеме нельзя понять, что ключи — это даты в формате `YYYY-MM-DD` или строки из цифр `"17"`. А это нужно, чтобы сортировать их или писать `get /by_id/17`.

### 8. Взрыв вариантов и мапа дат: цена в токенах

Ожидал: одну запись с 6 необязательными полями; мапу дат меньше данных.

```
> shape | count   (stdin: sparse.json, 300 records, id + 6 fields each present at 50%)
62
> shape | print | count   (stdin: sparse.json)
5187
> shape | elide 300   (stdin: sparse.json)
::shape[
  #[
    {
      :id ::number
      :a ::number
      :b ::number
      :c ::number
      :d ::number
      :e ::number
      :f ::number
    }
    ::elision{:size 61 :read ~(get /0 | drop 1)}
  ]
]
> shape | print | count   (stdin: dates.json, 365 date keys -> number)
9880
> shape | elide 200   (stdin: dates.json)
::shape{
  :rates ::elision{:size 365 :read ~(get /rates)}
}
```

(В строке `shape | count` я на самом деле запускал `shape | get /0 | count`. Неточная подпись — моя ошибка.)

Здесь `shape` теряет смысл. В первом случае 62 варианта, 5187 символов, 42% данных, а ответ на вопрос «какие поля необязательны» так и не дан. Под `elide` виден только первый вариант, и он вводит в заблуждение: все шесть полей выглядят обязательными. Во втором случае схема больше данных. Тип TypeScript для первого случая — одна строка `{id:number; a?:number; …; f?:number}[]`. pandas выдал бы 7 dtypes и счётчик non-null.

Схема этого не говорит, и придётся отдельно делать `get /price`. Так же поступают TypeScript и dtype `object` в pandas. Пример значения у листа сократил бы один шаг.

```
::shape[{:s ::set}]
```

Тег верхнего уровня снимается, а вложенный становится непрозрачным листом. Поэтому `/t/w` по схеме не прочесть, а `{:w 1}` и `{:w "a"}` под `::Box` сливаются в `::each::Box`, и разница видов скрыта. Множество тоже лист: что лежит в `#[{"a": 1}]`, не видно. Для цитаты и дока листовой вид правилен. Для тега и множества — нет: это контейнеры, и путь `get` читает сквозь тег (см. проверку ниже).

### 11. Сравнение с `paths`

```
> {"users": [{"name": "Ann", "age": 30}, {"name": "Bo"}, {"name": "Cy", "age": "41"}]} | paths
#[[/users/0/age ::number] [/users/0/name ::string] [/users/1/name ::string] [/users/2/age ::string] [/users/2/name ::string]]
> {"users": [{"name": "Ann", "age": 30}, {"name": "Bo"}, {"name": "Cy", "age": "41"}]} | shape | paths
#[[/users/0 ::set]]
```

`paths` — это `paths(scalars)` из jq с видами. Он растёт с данными и не сворачивает индексы, так что как схема не годится. `shape | paths` вырождается в одну пару из-за множества вариантов. Если бы элемент был одной записью, `shape | paths` дал бы готовый список путей для `get`, и это было бы очень удобно.

---

## Альтернативная форма

**Предложение.**

- **Один элемент на вектор.** Ключи всех записей объединяются. Поле, которого нет хотя бы в одной записи, получает `::absent` во множестве видов (это `?` из TypeScript). Множество вариантов-записей не строится. Записи сливаются ключ за ключом на любой глубине, а мапа `{}` уступает так же, как уступает `[]`.
- **`::each` по числу и виду ключей, а не только по форме значений.** Мапа сворачивается, если в ней больше 8 ключей одной формы с учётом `::absent`, атомы тоже считаются. Сворачивается и мапа, ключи которой — не идентификаторы: цифры, даты, UUID. Мапа с немногими ключами-именами остаётся записью. В схему можно класть `::each` с одним ключом-примером, если qlang разрешит такой литерал.
- **Тег и множество — прозрачные контейнеры:** `::Box{:w ::number}`, `::set[{:a ::number}]`. Так `#[…]` остаётся объединением, а множество данных пишется тегом над вектором.

Все литералы ниже читаются в текущем qlang:

```
> ::shape{:users [{:name ::string :age #[::absent ::null ::number ::string]}]} | get /users/0/age
#[::absent ::null ::number ::string]
> ::shape{:users [{:name ::string :age #[::absent ::null ::number ::string]}]} | get /users/0/age | has ::absent
true
> ::shape{:t ::Box{:w ::number} :s ::set[{:a ::number}]} | get /t/w
::number
> ::shape{:t ::Box{:w ::number} :s ::set[{:a ::number}]} | get /s/0/a
::number
> ::shape{:rates ::each::number} | get /rates
::each::number
> ::shape{:config {:db {:host ::string} :cache {:host ::string}}} | print | count
79
```

**Ответы на прогнанных случаях:**

- Случай 2:
  `::shape{:users [{:name ::string :age #[::absent ::null ::number ::string]}]}`
  `/users/0/age` читается, а `::absent` прямо говорит «пиши `query`».
- Случай 3:
  `::shape[{:a #[::absent ::number] :b #[::absent ::number] :c #[::absent ::number] :d #[::absent ::number]}]`
  и `::shape[{:id ::number :x #[::absent ::null ::number]}]`, `::shape[{:u {:a ::number :b #[::absent ::number]}}]`, `::shape[{:a {:x #[::absent ::number]}}]`.
- Случай 7, 8 строк вместо 60:
  ```
  ::shape{
    :items [{
      :id ::number :name ::string
      :score #[::number ::string]
      :email #[::absent ::null ::string]
      :tags #[::absent [::string]]
      :meta #[::absent {:src ::string :ts ::string}]
    }]
    :count ::number
  }
  ```
  `"n/a"` виден в `/items/0/score` сразу.
- Случай 8: `::shape[{:id ::number :a #[::absent ::number] :b #[::absent ::number] :c #[::absent ::number] :d #[::absent ::number] :e #[::absent ::number] :f #[::absent ::number]}]`. Около 170 символов против 5187. Мапа дат: `::shape{:rates ::each::number}`, около 30 символов против 9880.
- Случай 6: `{:u1 {:id 1} :u2 {:id 2 :admin true}}` даёт `::shape{:u1 {:id ::number} :u2 {:id ::number :admin ::boolean}}`: два ключа-имени, сворачивания нет. Те же записи под ключами `"17"`/`"42"` дают `::each{:id ::number :admin #[::absent ::boolean]}`. `:config` остаётся `{:db {…} :cache {…}}`.
- Случай 10: `::shape{:t ::Box{:w ::number} :q ::quote :d ::doc :s ::set[::number] :p ::path :n ::Width#::number}`. Последнее — вид под тегом-числом; если `#` над тегом не прочтётся, остаётся `::Width`.

**Что даёт.**

- Путь данных читает схему везде, кроме ключа под `::each`: `/users/0/age`, `/t/w`, `/s/0/a`.
- Необязательность видна у самого поля, как `?` в TypeScript и `required` в JSON Schema.
- Размер схемы зависит от числа полей, а не от их сочетаний.
- `shape | paths` снова становится списком путей для `get`.

**Чего стоит.**

- Теряется знание, какие поля встречаются вместе. Размеченные объединения вроде `{type:"a", x} | {type:"b", y}` превращаются в «всё необязательно». Это та же потеря, что у вывода типов в quicktype. Компромисс: оставлять множество записей, только если записи не имеют ни одного общего ключа.
- Порог «больше 8 ключей» и распознавание ключей-данных — эвристика. Мапа из 9 настоящих имён одной формы свернётся по ошибке.
- `::absent` — новый тег вида, его нужно описать на странице `::shape`.

**Чего нет в qlang.**

- Чтобы путь `/by_id/17/name` читал схему через `::each`, `get` должен понимать `::each` как подстановку любого ключа. Сейчас он отвечает `KeyNotInMapError`, так что это изменение семантики `get`, а не только `shape`.
- Размеров в схеме нет, и в этой форме я их не предлагаю: число внутри `[…]` сломало бы `/0`. Отдельное слово или поле рядом (`count`, `keys | count`) обходится дешевле, чем менять литерал схемы.
