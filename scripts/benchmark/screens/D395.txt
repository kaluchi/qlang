[
  [
    ::qlang
    |~~ qlang is a pipeline query language over values. A query starts
      from a subject, the value it is given, and passes it through steps:
      each step takes the value the step before answered and answers a
      new one, and the last answer is the answer of the query. Nothing
      changes in place. Everything the language handles is a value with
      a literal that prints and reads back as itself, data, code, prose
      and failures alike, so the language describes itself in its own
      values: every name has a page, the pages grow from ::qlang, and a
      query reads them as it reads any data.

      1. The pipe. `a | b` runs b on the value a answered, its subject:
      `[3 1 2] | sort | first` answers `1`. Each step is a command, a
      verb and what it takes, and a value stands where it is the
      subject, at the head or after a declaration, or as what a verb
      takes:
      `get /users | filter /active | sort /age | map /name` reads the
      users, keeps the active ones, ranks them by age and answers their
      names. A value written as a later step is refused.

      2. Values. Every value has a kind, a tag that `type` answers:
      `[1 2] | type` answers `::vec`. A value is written as its literal,
      which opens with the sign of its kind and closes with its pair, and
      everything between is literal: a literal reads no name and no
      subject, so it is the value it writes. Numbers, ::number, are
      finite doubles: `42`, `-1.5`. Strings, ::string: `"text"`.
      Keywords, ::keyword, are names that stand for themselves: `:name`.
      Booleans and null: `true`, `false`, `null`. Vectors, ::vec:
      `[1 2 3]`. Maps, ::map, have keyword keys: `{:a 1 :b 2}`. Sets,
      ::set, hold no duplicates and keep one order: `#[3 1 3]` answers
      `#[1 3]`. A tag written before a literal puts the value under it,
      `::Box{:w 2}`, a number, a boolean, null or a path touching it by
      `#`, `::Width#5`. JSON is a literal too and pastes into a query as
      it is, its keys read as keywords: `{"a": [1, 2]}` answers
      `{:a [1 2]}`. A keyword is not its string: `:a | eq "a"` answers
      `false`, and `toString` and `toKeyword` turn one into the other,
      `:a | toString` answering `"a"`.

      3. Reading parts. A path, ::path, names a part of a value: `/k` a
      key, `/0` an element, `/-1` the last, `/a/b/0` a part at depth. A
      path is a value and does nothing by itself; the verb that takes it
      reads it. `get` reads it and refuses a part that is not there:
      `{:a {:b [10 20]}} | get /a/b/-1` answers `20`. `query` reads it
      softly and answers null where the part is missing, or the default
      it is given: `{:a 1} | query /b 0` answers `0`. `has /b` asks
      whether the part is there, and `it` is the value itself.

      4. Commands. A command is a verb and what it takes, separated by
      spaces: `add 1`, `split ","`, `take 2`, `get /price`. The verb is
      found through the kind of the subject: `count` counts the elements
      of a vector and the characters of a string. Every modifier is
      computed once, at the call, against the subject of the step, and
      the verb receives the values: `10 | add 3` answers `13`. The
      subject of a step is what the step before it answered, so in
      `{:price 4 :qty 3} | get /price | mul (get /qty)` the `/qty` is
      read from the price, a number with no parts, and the call is
      refused, `::path/SubjectHasNoPartsError`: two values of one
      record are read in one step, `get [/price /qty]`, or combined by a
      verb that reads them, `{:price 4 :qty 3} | mulOf /price /qty`
      answering `12`. A modifier of more than one word stands in
      parentheses: `[1 2 3] | take (count | sub 1)` answers `[1 2]`.

      5. Code. A quote, `~(…)`, is code, and a quote computes to itself,
      so the verb receives it unrun and runs it where it needs. `map`
      runs its code on each element, that element its subject:
      `[1 2 3] | map ~(mul 2)` answers `[2 4 6]`. A path is code too, the
      code that reads it from each element: `[{:n 2} {:n 1}] | sort /n`
      answers `[{:n 1} {:n 2}]`. `filter` keeps the elements its code
      holds of, `[1 2 3] | filter ~(gt 1)` answering `[2 3]`; `groupBy`
      files the elements under what its code answers, or under
      themselves, `["b" "a" "b"] | groupBy | map ~(count)` answering
      `{:b 2 :a 1}`; `reduce` folds the elements into a seed, calling
      its verb with the value so far as the subject and the element as
      its first arg, `[1 2 3] | reduce 0 ~(add)` answering `6`, and
      running any other code on the pair of the two,
      `[{:n 1} {:n 2}] | reduce 0 ~(sumOf /0 /1/n)` answering `3`.
      Several steps stand in one quote,
      `[{:price 3}] | map ~(get /price | mul 2)` answering `[6]`, and
      `apply` runs its code on the subject itself,
      `5 | apply ~(add 1 | mul 2)` answering `12`. Without the quote, a
      group is a modifier computed at the call: in
      `[{:n 1}] | map (get /n)` the `/n` is read from the vector itself,
      not from each element, and `map` refuses what it is handed,
      `::vec/map/code/KindNotTakenError`.

      6. Building answers. An answer of a new shape is built by `get`
      over a template, a literal of paths and quotes, each path read and
      each quote run against the subject:
      `{:first "Ann" :age 30} | get {:who /first :next ~(get /age | add 1)}`
      answers `{:who "Ann" :next 31}`, and `{:a 1 :b 2} | get [/b /a]`
      answers `[2 1]`; `query` reads the paths of a template softly. A
      group or a name written inside a literal is refused, and a value
      computed goes under a tag by `tag`, `1 | add 2 | tag ::Box`.

      7. Names. A step sees only the value handed to it: after
      `get /qty |` the subject is a number, and the record it came from
      is gone unless a name keeps it. `:r it` names the value in the pipe
      `r`, and `:n (…)` names what its group computes; the value in the
      pipe goes on unchanged, and the bare word reads the name back, `:r`
      staying a keyword:
      `{:qty 2 :price 3} | :r it | get /qty | mul (r | get /price)`
      answers `6`. A name holds code as it holds any value, and a verb
      that takes code takes the name bare:
      `:double ~(mul 2) | 5 | apply double` answers `10`, and
      `:double ~(mul 2) | [1 2 3] | map double` answers `[2 4 6]`.
      Declared under the label of the values it serves, the code is a
      verb the name calls, `:number/double ~(mul 2) | 5 | double`
      answering `10`, which in the reader's own queries shadows a verb of
      that name on a broader label, `::any` among them, and which no verb
      of the root sees under a label of the root. A name is declared once
      in a scope, and the names
      a group or a quote declares stay in it.

      8. Elements and order. `count`, `sum`, `avg`, `min`, `max`,
      `first` and `last` read the elements of a vector, a set or a map.
      A map's elements are its values, the keys travelling with them:
      `{:a 1 :b 5} | filter ~(gt 2)` answers `{:b 5}`, and
      `{:a 1 :b 5} | map ~(add 1)` answers `{:a 2 :b 6}`. `keys` answers
      its keys, and `entries` the pairs `[key value]`, which `toMap`
      builds back into a map. One order ranks every value, so anything
      sorts: null, then booleans, numbers, strings, keywords, vectors,
      sets, maps. `desc` turns a key to descend:
      `sort ~(get [~(get /n | desc) /name])` ranks by n descending, then
      by name.

      9. Conditions. A condition is a boolean, and nothing else is
      truthy: `filter` and `if` refuse any other value. `if` takes the
      condition as a modifier and its two branches as code:
      `5 | if (gt 0) ~("pos") ~("neg")` answers `"pos"`. Conditions of
      one value hold together by `allOf` and `anyOf`, whose modifiers
      are computed at the call, every one of them, so a condition that
      may fail where an earlier one does not hold is written as a quote
      that answers it in its turn:
      `filter ~(allOf (get /email | ne null) ~(get /email | endsWith ".org"))`.

      10. Text. A string splits into a vector and joins back,
      `"a,b,c" | split "," | join "-"` answering `"a-b-c"`; `lines`
      breaks text into its lines, and `trim`, `lower`, `upper`,
      `contains`, `startsWith` and `endsWith` read it. A string is never
      read as a number behind the reader's back: `toNumber` reads one,
      `"42" | toNumber | add 1` answering `43`. A regex, `#"…"`, is
      written as the engine reads it, no backslash doubled, and reads
      text: `"took 12ms" | match #"(\d+)ms" | get /1` answers `"12"`,
      and `capture` answers the groups it names as a record.

      11. Failures. A step that fails answers a failure, a value under
      the tag of what refused: `"x" | add 1 !| type` answers
      `::number/add/SubjectNotNumberError`. `|` passes a failure by, and
      `!|` alone catches it, its step running on the error at rest, a
      value like any other: `"x" | add 1 !| 0` answers `0`. No value
      holds a failure, so a template whose quote fails answers the
      failure, while an error at rest, written `!{:k 1}`, sits anywhere
      and `raise` raises it. A failure carries its facts and its trace,
      a frame for each step it passed, the subject the step met and the
      steps from the one that failed, `::frame["x" ~(add 1)]`, and prints
      as an alert: the subject where it arose cut to an excerpt, and each
      subject it passed an ::elision where the elision prints shorter,
      whose `:read` continues the query to it, `!| get /trace/1/0`.
      `!| explain` answers the page of what refused above the failure,
      the page saying how to repair the call.

      12. Asking. `::vec | manifest` answers what lies under a kind, its
      verbs, its refusals and the roles of its chain, and `map` asks
      several kinds at once, each beside its own:
      ::snippet~([::vec ::map ::string ::number ::any] | map ~(get [~(it) ~(manifest)]))
      lists the verbs most queries use. `::vec/sort | doc` answers the
      page of a verb, and `::vec/sort | laws` the laws of a verb by
      name, each a page and a query that answers true; `x | type | doc`
      answers the page of the kind of any value. An answer prints whole;
      `x | elide 4000` bounds it to four thousand characters of its
      print, each part left out an ::elision whose `:read` continues the
      query to it.

      13. A task. Over
      `{"users": [{"name": "Ann", "age": 30, "tags": ["a", "b"]}, {"name": "Bo", "age": 15, "tags": []}]}`,
      `get /users | filter ~(get /age | gte 18) | map ~(get {:name /name :n ~(get /tags | count)})`
      answers `[{:name "Ann" :n 2}]`. Look at the data before shaping
      it, `shape` its structure, the kind at each of its parts, `keys`,
      `get /0`, `type`, `count`, and build the query a step at a time,
      running each.

      14. The chapters, in the order they rest on each other:
      ::link~(::qlang/values | doc) values, kinds and tags;
      ::link~(::qlang/pipeline | doc) the steps of a query;
      ::link~(::qlang/names | doc) names and their records;
      ::link~(::qlang/verbs | doc) the verbs that live on kinds;
      ::link~(::qlang/errors | doc) the failure as a value;

      ::link~(::qlang/hypertext | doc) the pages and how to move through
      them;
      ::link~(::qlang/hosts | doc) the tool the language runs in and the
      budget of an answer.
  ~~|

  [
    ::cli
    |~~ The command line runs a query on what a shell hands it and prints
      the answer: `qlang 'get /users | count' < data.json` in a script, and
      `qlang -i` a session of cells. It is the host a reader meets first,
      and the verbs it adds read and write the streams of the process.

      A query runs on what stdin holds. JSON is read as values, an object
      a map whose keys are keywords, `{"name": "Ann"}` arriving as
      `{:name "Ann"}`; any other text is one string, and `--raw` reads
      JSON text as a string too. A query that reads no subject,
      `qlang '::vec | doc'` or `qlang '[1 2] | sum'`, runs at once and
      reads no stdin. One that reads it with nothing piped, a terminal or
      `< /dev/null`, runs on the noun of the language, `::qlang`, so
      `qlang 'doc'` reads the first page; where a shell leaves stdin
      open, it waits for the end, as every reader of a pipe does.

      The answer is printed as the language prints it, whatever the data
      was: a map as `{:name "Ann" :tags #["a"]}`, a kind as `::map`. A
      string goes out as its text, so a query that ends in a conversion
      writes what the conversion made: `| json` the JSON text of the
      answer, `| table` a vector of maps drawn as a table, `| print` the
      literal of the answer, a string in its quotes. A failure prints as
      its alert, the error at rest `::Tag!{…}` with the subject where it
      arose cut to an excerpt, under the line
      `|~| raised, and no !| caught it` and above the prose of its
      refusal's page as line comments `|~| …`, which tells how to repair
      the call, a refused text with a caret under the line the alert shows
      between the two; `!| json` writes a failure as JSON. Every answer
      goes to stdout with the exit code 0, a failure among them, a query
      that does not parse answering `::quote/ParseError`, so calls run side
      by side never stop each other. A script that tests the code
      writes `--fail` before the query, `qlang --fail 'get /id' < a.json
      && next`: a failure exits with 1, written as without it.

      An answer prints whole, and `--budget=N` or `| elide N` bounds it,
      what is left out an `::elision` whose `:read` continues the query
      to it. `in`, `out`, `err` and `tap` read and write the
      streams, `tap` showing a value halfway through a query on stderr;
      a query that writes to stdout by `out` holds the channel, and its
      answer is left unwritten. A value one query hands another over a
      pipe keeps its kinds as its literal, `print | out` writing it and
      `in | parse | open` reading it back.
